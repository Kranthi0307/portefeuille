Shared Service

A reusable Java library for sharing common Spring components, configuration properties, tenant-context utilities, and persistence helpers across services.

Overview

This library packages code intended to reduce duplication across the Spring services I build. It is distributed as a JAR and uses Spring Boot auto-configuration to register selected components in Servlet/Reactive-based applications.

The library provides shared building blocks; consuming services remain responsible for their application-specific security, API behavior, persistence setup, and configuration.

Purpose

When multiple services need the same common capabilities, teams can end up building and maintaining them separately. This project brings selected shared components into one reusable library, making them easier to apply consistently and update in one place. It provides common building blocks; each service still controls its own business rules and security.

Features

  • Spring Boot auto-configuration for selected Servlet/Reactive application components and configuration properties.
  • Tenant context utilities using a ThreadLocal to make request-scoped user and tenant information available to downstream code.
  • Hibernate tenant identifier resolution based on the current tenant context, with a fallback identifier during application startup.
  • JPA auditing base classes and listeners for creation and update timestamps and usernames.
  • Reusable types and utilities, including response and user-information records, validation-group markers, date/string helpers, and custom exception types.

Scope and limitations

  • Reactive/WebFlux support is not implemented, to use ThreadLocal.
  • This library does not provide API endpoints or a global HTTP exception handler.
  • Configuration-property records are provided, but defining a property does not by itself configure a corresponding security or CORS policy.
  • The tenant filter is not an authentication mechanism. Review its behavior and integration with the consuming application before enabling it.
  • The repository does not currently contain test sources.

Architecture

In a Servlet application, the tenant-related components can work together as follows. The host application is responsible for supplying appropriate request identity and tenant information and integrating the filter with its request-processing setup.

TenantIdentifierResolver returns the startup fallback tenant identifier before the application context is initialized. At runtime, it obtains the tenant identifier from UserInfoContext; if there is no tenant in the context, it throws an IllegalStateException.

Prerequisites

  • JDK 17
  • A shell that can run the Maven wrapper

Build and test

Build the JAR locally:

mvn clean package

To install the artifact into your local Maven repository for use by another local project:

mvn clean install

The Maven coordinates declared by this project are:

com.kranthi:shared-service:1.2.0

A local consumer can then declare the dependency in its pom.xml:


<dependency>
    <groupId>com.kranthi</groupId>
    <artifactId>shared-service</artifactId>
    <version>1.2.0</version>
</dependency>

Configuration

The auto-configuration enables these typed property groups:

Prefix Purpose
config.web Public and administrative endpoint path patterns
config.others Development mode and tenant-related settings
config.cors CORS-related property values

Example configuration using safe, illustrative values:

config:
  others:
    dev-mode: false
    tenant-id: 1
    tenant-enabled: false
    tenant-excluded-paths:
      - /actuator/health
  cors:
    allowed-origins:
      - https://example.com
    allowed-methods:
      - GET
      - POST
    allowed-headers:
      - Authorization
      - Content-Type
    exposed-headers:
      - Authorization
    allow-credentials: true
    max-age: 3600

Property defaults are defined in the library and can vary by version. Set values explicitly for the consuming service rather than relying on defaults.

Tenant filter caution: The Servlet tenant filter uses the configured development-mode and tenant settings and supplies a development username. Do not treat it as production authentication or authorization. Check the filter’s registration and ordering in the host application, and use the host application’s security configuration for access control.

UserInfoContext uses a thread-local value. Code that sets the context must ensure it is cleared when processing finishes; the provided tenant filter clears it in a finally block.

Persistence helpers

The Events mapped superclass provides created_at and updated_at fields, populated by a JPA lifecycle listener. EventInfo extends it with created_by and updated_by, populated from UserInfoContext.

These are reusable base classes, not concrete entities. Consuming applications provide their own entities, repositories, database configuration, and schema management.

Version history

v1.2.0

This release included:

  • Auto-configuration for Servlet/Reactive applications: Registers the startup component and shared service, and conditionally provides tenant-related beans when tenant support is enabled.
  • Tenant context and Hibernate integration: Provides UserInfoContext and TenantIdentifierResolver for resolving the current tenant from thread-bound context.
  • Servlet tenant filter: Provides a filter that sets development tenant context when development mode is enabled. It is not an authentication mechanism; consuming applications must configure security and filter integration appropriately.
  • Shared data types: Includes ResponseRecord<T> and UserInfo.
  • JPA audit base classes: Includes Events and EventInfo with lifecycle listeners for timestamps and username fields.
  • Configuration properties: Includes SharedWebProperties, SharedDevProperties, and SharedCorsProperties.
  • Shared exception types: Includes BaseException and domain-specific subclasses.
  • Validation markers and utilities: Includes create/update validation groups, constants, and date/string helper methods.
