ERROR HANDLING LIBRARY

A spring boot library, for an enterprise-level error handling.

Why?

  • Native Multi-Stack Support: Eliminate the friction of forcing reactive applications into servlet wrappers or dealing with clunky bridging logic. Both Servlet and Reactive worlds get native, first-class error handling.
  • Modular Flexibility: Avoid monolithic, tangled error handlers. By cleanly separating concerns into Security, Web and others modules, applications only adopt the exact slices they actually need.
  • Zero-Conflict Control: Stop worrying about drop-in libraries stepping on existing code. Granular @ConfigurationProperties toggles give developers the power to enable or disable any piece of the library on the fly without breaking custom setups.
  • Enterprise Consistency: Establish a predictable, standardized error structure(ProblemDetail) across teams and microservices right out of the box.

Key Features

  • Dual-Stack Native Support (Servlet & WebFlux): Built from the ground up for both worlds. Whether your application runs on traditional Spring MVC (Tomcat) or non-blocking reactive Spring WebFlux (Netty), it gets idiomatic, high-performance error handling without forced bridges or blocking wrappers.
  • Layered Modular Architecture: Cleanly separated into logical modules so you only include or reason about what you need:
    • Security Module: Out-of-the-box, clean mapping for authentication (401 Unauthorized) and authorization (403 Forbidden) failures.
    • Web Module: Seamless wrapping of framework-level issues (type mismatches, missing parameters, method arguments) using Spring’s ResponseEntityExceptionHandler equivalents.
    • Common Module: Reliable handling for custom domain exceptions, low-level database errors ( DataAccessException) and global catch-all fallback safety nets.
  • Granular @ConfigurationProperties Toggles: Total control at your fingertips. Every single sub-module across both Servlet and Reactive stacks can be independently enabled or disabled (true/false) in your application.yml, preventing conflicts with existing application code.
  • Standardized RFC 7807 (Problem Details) Responses: Ensures all error payloads follow a consistent, machine-readable standard (type, title, status, detail, instance) making life easier for API clients and frontend consumers.
  • Zero-Magic, Non-Invasive Integration: Designed to drop into enterprise projects seamlessly. It respects your application's existing configurations and custom overrides, letting you adopt it piece-by-piece.

Architectural Decision Records

ADR 1: Dual-Stack Support (Servlet vs. Reactive Architecture)

  • Context: Spring developers are split across two worlds: the traditional Servlet world (Spring MVC with Tomcat) and the newer, non-blocking Reactive world (Spring WebFlux with Netty). Because these two environments handle exceptions completely differently under the hood, a one-size-fits-all approach doesn't work.
  • Decision: Instead of forcing a messy bridge between the two, I built two parallel tracks right from the start: servlet and reactive. Each stack uses its own native Spring error-handling mechanisms.
  • Pros: MVC developers get clean, idiomatic MVC code and WebFlux developers get true non-blocking reactive handling. Nobody suffers from slow performance or leaky abstractions.
  • Cons: We do have to maintain equivalent logic in two parallel places.

ADR 2: Modular Component Separation (Security, Web, etc.)

  • Context: Error handling happens at different layers of an application. Security failures (like a 401 or 403) look very different from framework validation errors, which in turn look different from database crashes or custom domain rules. If we threw everything into one giant class, it would turn into a maintenance nightmare.
  • Decision: I split each stack into three clear, bite-sized modules:
    • security: Manages authentication and permission issues (401s and 403s).
    • web: Handles all the standard framework headaches like missing request params, bad types and validation failures.
    • Others: Catches custom business logic exceptions, database errors (DataAccessException) and acts as the safety net for unexpected crashes.
  • Pros: It keeps code clean, focused and super easy to test. It also means applications can pick and choose what they actually want to use.

ADR 3: Granular Feature Toggling via @ConfigurationProperties

  • Context: Drop-in libraries can sometimes be a little too aggressive. If an auto-configured error handler steps on the toes of an application's existing custom setup, it causes annoying startup conflicts or unexpected response changes.
  • Decision: I gave developers an escape hatch. Every single sub-module (servlet vs. reactive, across security, web and others) comes with its own @ConfigurationProperties toggle so you can flip them true or false independently.
  • Pros: Complete flexibility. If an application wants to use this web error handlers but keep its own custom security rules, it can just switch security off in the configuration. No magic friction.

Future Enhancements

  • Out-of-the-Box Observability: Automatically attach live Micrometer traceId values to every error response to drastically cut down debugging time in distributed systems.
  • Proactive Security & Masking: Intercept and sanitize sensitive query parameters, secrets, raw SQL exceptions and internal stack traces before they leak out to clients.
  • Seamless Localization: Dynamically resolve error titles and descriptions based on incoming Accept-Language headers using standard Spring MessageSource configurations.
  • Advanced SPIs & Custom Hooks: Expand Service Provider Interfaces (SPIs) and @ConditionalOnMissingBean integrations to let teams easily swap default behaviors for advanced enterprise rules.

Versions

v0.1.0

  • Domains:
    • BusinessException that serves as the parent for all custom, domain-specific exceptions throughout the ecosystem.
    • ValidationError with field and its message.
  • Properties: Each property has enabled field making it accessible to disable the beans that are not needed.
  • Configurations:
    • For Servlet, beans enabled by default are globalExceptionHandler, businessExceptionHandler, servletPersistenceExceptionHandler, servletAuthenticationEntryPoint, servletAccessDeniedHandler and servletWebExceptionHandler
    • For Reactive, beans enabled by default are globalExceptionHandler, businessExceptionHandler, reactiveAuthenticationEntryPoint and reactiveAccessDeniedHandler

If error.handling.reactive.security.enabled=true or error.handling.servlet.security.enabled=true, the respective Security Configurations are to be implemented in the application.

For example:

.authenticationEntryPoint(authenticationEntryPoint)
.accessDeniedHandler(accessDeniedHandler)
