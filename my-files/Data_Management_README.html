Data Management

A developer-facing data management application for maintaining products and their referential data. It combines an Angular web interface with a Spring Boot REST API backed by PostgreSQL.

Purpose

Product and category data often needs to be changed as development work progresses. Managing those changes through manual database updates can be slow and difficult to track. This project provides a central interface and API for developers to manage product data and its supporting reference information, while keeping records organized by tenant and allowing archived records to be restored.

The goal is to make routine data-management tasks easier to perform and maintain, not to replace the external processes that permanently clean up archived data.

Overview

The application provides a UI and API for managing:

  • Referential types and referentials, which organize product categories and related reference data.
  • Products, including their descriptions, prices, details, and category associations.
  • Archived records, which can be listed and restored through API operations.

Permanent deletion is handled by cron jobs configured externally; those jobs are not part of these repositories.

Architecture

The project is split across two repositories: the Angular UI (dev-support-ui) and the Spring Boot API ( dev-support-service).

The UI calls the API through Angular HTTP services and Gateway. Shared UI code handles authentication-related requests and adds request headers; protected UI routes use an authentication guard. On the backend, REST resources delegate to service classes, which use Spring Data JPA repositories to access the database.

Features

  • Create and update products, referential types, and referentials.
  • Browse and filter product and referential data in the UI.
  • Archive records and restore archived records.
  • Protect API routes with Spring Security and JWT-based authentication.
  • Associate requests with tenant and user context.
  • Generate OpenAPI documentation for the service.

Prerequisites

  • Java 17
  • Node.js and npm versions supported by Angular 19
  • PostgreSQL for local service development
  • Access to the service's shared-library dependency

The service uses a shared library distributed through a package registry. For access and setup, consult that library's README.

Getting started

1. Start the service

From the service repository root:

gradle bootRun

Run the service tests with:

gradle test

The service is configured to use the dev profile by default. Its current configuration sets the server port to 8085 and the context path to /dev-service; use environment-specific overrides as needed.

The development tenant-context option can be enabled with config.others.dev_mode=true and configured with config.others.tenant-id=<tenant-id>. This lets the tenant filter use development context instead of reading tenant details from a JWT. The Spring Security configuration still enables JWT resource-server authentication for protected requests; configure the local security setup accordingly if you need to run those requests without an authentication issuer.

2. Start the UI

From the UI repository root:

npm install
npm start

The Angular development server runs at http://localhost:4200 by default. The start script uses proxy.config.json to proxy API paths. That file currently targets port 2000, while the service configuration uses port 8085; align the proxy target with the service address you run locally.

Build the UI with:

npm run build

The UI's development environment uses a relative API base URL and relies on the development proxy. Set an appropriate API base URL in the environment configuration used for deployment.

API overview

The service groups its routes under these base paths, below the configured /dev-service context path:

  • /product-api/v1 - product operations and product archive retrieval.
  • /referential-api/v1 - referential and referential-type operations and archive retrieval.
  • /archive-api/v1 - record restoration.

API details are generated from the service's OpenAPI annotations. With the development configuration enabled, Swagger UI is typically available at:

http://localhost:8085/dev-service/swagger-ui/index.html

The service security configuration protects product and referential routes with role-based authorization. Configure valid local authentication as required by the active security setup.

Authentication and tenant context

The UI has shared authentication code for login, status checks, logout, and token refresh. Its HTTP interceptor attaches available authorization, tenant, and XSRF headers, and attempts a refresh after an unauthorized response.

The service validates JWTs through Spring Security. Its tenant filter reads tenant and user information from the authenticated request, or uses configured development context when development mode is enabled. Do not use development tenant settings as a substitute for production authentication and tenant isolation.

Database and archive behavior

Liquibase changesets define tables for products, product details, referentials, referential types, and the recycle bin. The product and referential records include tenant and audit fields; the recycle bin stores serialized record data for restoration.

Archiving and restoration are exposed by this service. Permanent cleanup is external: scheduled cron jobs are configured outside these repositories.
