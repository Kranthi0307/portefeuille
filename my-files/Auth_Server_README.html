Authentication Server

A Spring Boot service for user registration and authentication, with JWT issuance, refresh-token handling, tenant-aware request context, and a JWKS endpoint.

Purpose

Applications need a way to confirm who a user is before granting access. This project explores a shared authentication service that handles sign-in and issues time-limited access tokens that other services can verify.

It also includes tenant-aware request handling, so requests can be associated with the right organization or customer. The goal is to keep common identity and access tasks in one service rather than implementing them separately in each application.

This is under development project, as some management operations are still being developed.

Overview

The service uses Spring Security for authentication, stores application data in MySQL through Spring Data JPA, and manages database schema changes with Liquibase. Access tokens are signed with an RSA private key; the corresponding public keys are exposed as a JSON Web Key Set (JWKS).

The application is configured to start with its dev profile by default. This README describes development setup; it does not imply production readiness.

Features

  • Authenticate users and issue signed JWT access tokens.
  • Issue and validate refresh tokens; the refresh token is returned in a cookie.
  • Publish public RSA keys at GET /.well-known/jwks.json.
  • Register users and provide user, tenant, role, and privilege API resources.
  • Resolve a tenant from the X-TENANT request header for tenant-scoped requests and clear the request context afterward.
  • Apply Spring Security rules for public and authenticated endpoints.
  • Apply Liquibase changelogs automatically at startup.

Architecture and request flow

For tenant-scoped requests, TenantFilter reads the X-TENANT header, resolves the tenant, and stores its ID in TenantContext for the duration of the request. The context is cleared after the request is processed.

AuthResource delegates credential authentication to Spring Security, creates an access token through JwtService, and creates a refresh token through RefreshTokenService. JwksController returns public RSA key data for clients that need to verify tokens.

Prerequisites

  • JDK 17
  • MySQL
  • Access to the Maven artifact repository that provides shared-service
  • A development PKCS#12 keystore for JWT signing

Development setup

  1. Create a local MySQL database and a database user with the required permissions.

  2. Ensure the shared-service artifact is available to Maven. Consult that library's README for setup details.

  3. Configure the application using environment variables. Do not put credentials or private keys in source control.

  4. Run the application:

    mvn spring-boot:run

To build the application without starting it:

mvn clean package

The application uses the dev Spring profile by default. Liquibase is enabled and reads changelogs from db/changelog/changelog.yaml during startup.

Configuration

The development profile needs a MySQL datasource and a PKCS#12 keystore. Set local values through environment variables rather than copying credentials into YAML:

Environment variable Purpose
SPRING_DATASOURCE_URL JDBC URL for the local MySQL database
SPRING_DATASOURCE_USERNAME Local database username
SPRING_DATASOURCE_PASSWORD Local database password
CONFIG_KEYS_KEYSTORE Keystore resource location, such as file:/path/to/dev-keystore.p12
CONFIG_KEYS_PASSWORD Password for the development keystore
CONFIG_KEYS_TYPE Keystore type, normally PKCS12
CONFIG_KEYS_ACTIVE_ALIAS Alias used to sign access tokens
CONFIG_JWT_ACCESS_EXPIRATION Access-token expiration setting

Example shell configuration (replace every placeholder with a local development value):

export SPRING_DATASOURCE_URL='jdbc:mysql://localhost:3306/<database>'
export SPRING_DATASOURCE_USERNAME='<local-database-user>'
export SPRING_DATASOURCE_PASSWORD='<local-database-password>'
export CONFIG_KEYS_KEYSTORE='file:/path/to/dev-keystore.p12'
export CONFIG_KEYS_PASSWORD='<development-keystore-password>'
export CONFIG_KEYS_TYPE='PKCS12'
export CONFIG_KEYS_ACTIVE_ALIAS='<development-key-alias>'
export CONFIG_JWT_ACCESS_EXPIRATION='<expiration-value>'

CONFIG_JWT_ACCESS_EXPIRATION is passed to the token service as a number of minutes. The development configuration currently sets it to 5.

The repository's development YAML also contains settings beyond this table. Keep OAuth client credentials, database credentials, and all signing material out of public files and version control.

API surface and implementation status

The servlet context path is /auth. The following paths are defined in the current application:

Method Path Status
POST /auth/login Authenticates credentials and returns an access token; sets a refresh-token cookie.
POST /auth/refresh Validates the refresh-token cookie and returns a new access token.
POST /auth/logout Configured as a Spring Security logout endpoint.
POST /auth/register Registers a user.
GET /auth/.well-known/jwks.json Returns public key data in JWKS format.
POST /auth/tenant-api/v1/createTenant Creates a tenant.
POST /auth/user-api/v1/createUser Creates a user.
GET /auth/user-api/v1/fetchUsers Fetches users.
POST /auth/role-api/v1/createRole Creates a role.
POST /auth/role-api/v1/assignRole Route exists, but assignment logic is currently commented out.
POST /auth/role-api/v1/unAssignRole Route exists, but unassignment logic is currently commented out.
GET /auth/role-api/v1/fetchRoles Fetches roles.
POST /auth/privilege-api/v1/createPrivilege Creates a privilege.
POST /auth/privilege-api/v1/assignPrivilege Assigns a privilege to a role.
POST /auth/privilege-api/v1/unAssignPrivilege Removes a privilege from a role.
GET /auth/privilege-api/v1/fetchPrivileges Fetches privileges.
POST /auth/company-api/v1/createCompany Route exists, but persistence logic is currently commented out.

Request and response details are defined by the resource classes and domain types. Some management routes may require authentication or tenant context according to the security configuration and request filter.

Security notes

  • The keystore is for development only. Do not use it to sign production tokens.
  • Keep production private keys in a private secret store and provide them to the application through deployment configuration.
  • Never publish keystore files, passwords, OAuth client secrets, database credentials, or other tokens.
  • The JWKS endpoint exposes public key material, not the signing private key.
