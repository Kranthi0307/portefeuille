API Gateway

A reactive Spring Boot gateway for routing requests to downstream services, with JWT-based security and configurable CORS and CSRF protection.

Overview

This is the entry point for requests routed to configured services. It uses Spring Cloud Gateway with WebFlux and applies Spring Security and a custom gateway filter to requests.

Purpose

In a system made up of multiple services, clients need a consistent way to reach the right service without handling each service connection separately. This gateway provides that shared entry point and applies common request-handling and security checks before forwarding traffic. It also demonstrates how to organize routing and security in a reactive Spring application.

Features

  • Reactive HTTP gateway built with Spring Cloud Gateway and WebFlux.
  • Route definitions and route-specific filters configured in Java.
  • JWT authentication through Spring Security’s OAuth2 resource-server support.
  • CORS settings and cookie-backed CSRF token handling.
  • Custom gateway filter for request checks, including tenant-header validation.
  • An authentication-status endpoint at /api/v1/checkStatus.

Architecture and request flow

SecurityConfiguration defines the reactive security filter chain and CORS/CSRF setup. GatewayConfiguration declares routes, and AuthenticationFilter is applied to those routes before requests are forwarded.

Routes and access

Routes are defined in GatewayConfiguration.java:

Path pattern Purpose
/auth/** Authentication-service route
/portfolio/** Portfolio-service route

The custom AuthenticationFilter also requires the X-TENANT header on routed requests, including requests matching a public path. This behavior is currently present even though tenant support is set to disabled in application configuration. Do not assume that the setting disables the filter check.

Security and browser configuration

  • JWTs are validated by Spring Security as an OAuth2 resource server. The JWK Set URI is configured through application settings.
  • Authorities are derived from the JWT roles claim.
  • CORS policies are configured through application properties. Allowed origins, methods, headers, exposed headers, and credential handling are controlled by that configuration.
  • CSRF protection uses a cookie-backed token repository. The configured CSRF cookie is CID, and the corresponding request header is X-CID.
  • The CSRF cookie is configured as Secure, with SameSite=Lax.

Client applications must follow the configured CORS policy and send the CSRF token as required for protected requests. Do not infer the effective origin or header allowlist from this README; check the deployment-specific configuration.
